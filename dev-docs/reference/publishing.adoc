= Publishing Libraries

This guide covers everything needed to publish Wagoe libraries to Clojars — locally or via GitHub Actions.

---

== Prerequisites

=== Clojars account

Create an account at https://clojars.org[clojars.org] if you don't have one.

=== Deploy token

Clojars requires a deploy token — **not** your account password.

. Log in at https://clojars.org
. Go to *Profile → Deploy Tokens*
. Click *Generate Token*, name it (e.g. `wagoe-deploy`)
. Copy the token immediately — it is shown only once

The token looks like: `CLOJARS_XXXXXXXXXXXXXXXXXXXXXXXX`

=== Local environment variables

[source,bash]
----
export CLOJARS_USERNAME=your-clojars-username   # username, not email
export CLOJARS_PASSWORD=your-deploy-token        # token from above
----

Add these to your shell profile (`~/.zshrc` or `~/.bashrc`) for convenience.

== Version management

Each publishable artifact has a `(def version "…")` in its own `build.clj`.
This includes all 33 libraries under `libs/*` — `libs/tools` among them. It is
dev-only in the sense that applications do not depend on it at runtime, but it
is published like everything else, as `com.wagoe/wagoe-tools`.

The Git tag does not define the artifact versions.  It only triggers the
workflow.  Clojars versions are read from each artifact's `build.clj` at
publish time.

=== Bumping the version

[source,bash]
----
# Rewrites the version in every location bb check:versions governs — every
# build.clj and the documentation — then verifies the result.
bb bump NEW               # no leading "v"
bb bump NEW --dry-run     # list the files it would change
----

=== Version format

Wagoe follows semantic versioning:

* `1.0.0-alpha-N` — alpha release, N is a sequential counter
* `1.0.0-beta-N` — beta release
* `1.0.0` — stable release
* `1.0.1` — patch release
* `1.1.0-rc-N` — release candidate of the next minor (see the stability page for the naming rule)

[IMPORTANT]
====
Clojars does **not** allow overwriting an existing version.
Always bump the version before deploying — you cannot re-deploy the same version string.
====

== Deploying locally

=== All 33 artifacts in one command

[source,bash]
----
bb deploy --all
----

This deploys all 33 publishable artifacts in dependency order. There is no
pause between them: each library is installed into `~/.m2` first, so the next
one never waits on Clojars indexing.

=== Only libraries not yet on Clojars

[source,bash]
----
bb deploy --missing
----

Useful when resuming a partially failed deploy run.

=== Specific libraries

[source,bash]
----
bb deploy core platform user
----

=== Single library manually

[source,bash]
----
cd libs/core
clojure -T:build clean
clojure -T:build deploy
----

=== Verify publication

After deploying, check that the artifacts are visible on Clojars:

[source,bash]
----
bb deploy --verify    # fails unless every artifact is on Clojars at this version
----

Or open in a browser: https://clojars.org/com.wagoe/wagoe-core

== Deploying via GitHub Actions

The workflow is defined in `.github/workflows/publish.yml`.

=== One-time setup: GitHub secrets

The credentials live on the *`release` environment*, not on the repository —
the `publish` job declares `environment: release` (see <<approval-gate>>), so
repository-level secrets of the same name would not be what the job reads.

*GitHub → Settings → Environments → `release` → Environment secrets*

[cols="1,2",options="header"]
|===
|Secret name |Value
|`CLOJARS_USERNAME` |Your Clojars username (not email)
|`CLOJARS_PASSWORD` |Your Clojars deploy token (from clojars.org/tokens)
|===

Or from the CLI — the value is read from stdin and never echoed:

[source,bash]
----
gh secret set CLOJARS_PASSWORD --repo wagoebv/wagoe --env release
----

.Rotating the token
[NOTE]
====
Update the `release` environment secret *before* revoking the old token on
clojars.org, so no release can fail in between. Check where copies live first —
`gh api repos/wagoebv/wagoe/environments/<env>/secrets` lists names and
timestamps without exposing values.

Never echo a token to verify it is set. Use a presence test that cannot expand
the value:

[source,bash]
----
[ -n "$CLOJARS_PASSWORD" ] && echo set || echo "not set"
----
====

=== Trigger: push a version tag

This is the normal release flow:

[source,bash]
----
# 1. Bump the version everywhere. NEW has no leading "v": the workflow
#    triggers on unprefixed semver tags (1.0.1, 1.1.0-alpha-1).
bb bump NEW

# 2. Confirm every hard-coded copy of the version agrees before tagging
bb check:versions

# 3. Commit and tag
git commit -am "Bump version to NEW"
git tag -a NEW -m "Release NEW"
git push origin main
git push origin NEW
----

GitHub Actions will:

. **Wait for approval** — see <<approval-gate>> below; nothing runs until a maintainer approves
. **Require green CI on the tagged commit** — see <<ci-gate>> below; the release aborts in seconds if the commit was never tested
. Build the Tailwind CSS bundle (required for the `ui-style` jar)
. Check that every `build.clj` carries the release version (`bb deploy --check-versions`)
. Run `bb deploy --missing` with the Clojars credentials, so a re-run skips what already landed
. Check every artifact is on Clojars (`bb deploy --verify`)
. Create a GitHub Release. A version with a stage (`1.1.0-rc-1`) is marked pre-release, so `/releases/latest`, which
  `scripts/install.sh` installs, stays on the last final release. Try a pre-release through its Maven version
  (`{:mvn/version "1.1.0-rc-1"}`), not through `install.sh`.

=== Trigger: manual dispatch

For deploying without a tag (e.g. re-running after a partial failure):

. Go to *GitHub → Actions → Publish to Clojars*
. Click *Run workflow*
. Optionally enter the version to publish (defaults to the one in `libs/core/build.clj`)

[#approval-gate]
=== The approval gate

The `publish` job declares `environment: release`, a GitHub Environment with a
required reviewer. **Pushing a tag does not publish on its own** — the run stops
before its first step and waits.

To release, after pushing the tag:

. Go to *GitHub → Actions → Publish to Clojars* and open the pending run
. Click *Review deployments*, tick `release`, then *Approve and deploy*

A run left unapproved shows as waiting, not failed. If a tag push seems to have
done nothing, check for a pending approval before debugging anything else.

.Why an environment rather than an actor check
[NOTE]
====
This replaced `if: github.actor == 'thijs-creemers'` (BOU-248). That guard held
the right property — only a trusted human publishes — but expressed it as one
hardcoded login: no second maintainer could release, and it would fail *silently*
(job skipped, no error) if the account were renamed.

The tempting one-line fix, `github.repository_owner == 'wagoebv'`, is always true
for this repository. It would read as a gate while gating nothing, handing
publish rights to anyone with write access.
====

The Clojars credentials (`CLOJARS_USERNAME`, `CLOJARS_PASSWORD`) should be
*environment* secrets on `release` rather than repository secrets, so that no
other workflow or branch can read them. Environment secrets shadow repository
secrets of the same name, so the move is: set them on the environment, confirm a
release still works, then delete the repository-level copies.

[#ci-gate]
=== The CI gate

Approval proves a human wanted this release. It does not prove the code works.

The step immediately after checkout reads the GitHub Checks API for the tagged
commit and requires a completed, successful `All Tests Passed` — the same single
context branch protection requires to merge. Anything else aborts the run:

* **no run at all** — the commit never went through CI, so nothing has tested the
  source about to be published;
* **a run that failed** — and a run still going is waited for, up to 25
  minutes, then the release aborts: pending is not green.

Why this matters more here than anywhere else: Clojars coordinates are
*immutable*. A bad release cannot be recalled, overwritten or yanked; the only
way out is burning a version number and telling everyone who already resolved it.
Every other guard in the workflow protects the *shape* of a release — the tag
agrees with source (`--check-versions`), nothing is half-published (`--missing`),
everything landed (`--verify`). None of them asks whether the code works.

It reads the recorded run rather than re-running the suite, deliberately.
Re-running would double the release time and could pass on a flake the recorded
run had caught — and a release that means something different from a merge is
how the merge gate becomes optional.

The guard runs *before* the ~10 minutes of setup below, so a release that must
not happen costs seconds. `check:branch-protection` asserts that it exists and
that it precedes the deploy, on every pull request — the same no-token,
no-API trade the rest of that gate makes.

== What the workflow does

[source,yaml]
----
- Setup Clojure + Babashka       # DeLaGuardo/setup-clojure with bb: latest
- Cache ~/.m2 and ~/.gitlibs     # Speeds up subsequent runs
- Guard: CI passed on the commit # Waits up to 25 min for "All Tests Passed"
- npm ci + npm run build:css     # Builds Tailwind CSS for ui-style jar
- bb deploy --check-versions NEW # Every build.clj carries the release version
- bb deploy --missing            # Deploys what is not yet on Clojars, in order
- bb deploy --verify             # Every artifact landed
- Create GitHub Release          # Only on tag pushes; pre-release when the version has a stage
----

== Release checklist

Before pushing a release tag:

* [ ] All tests pass: `bb test:all` (not just `clojure -M:test` — see AGENTS.md on test surfaces)
* [ ] No lint errors: `clojure -M:clj-kondo --lint src test libs/*/src libs/*/test`
* [ ] All quality gates pass: `bb check` (a failing gate always exits non-zero;
  `--ci` is accepted but no longer needed)
* [ ] `CHANGELOG.md` updated
* [ ] Version bumped with `bb bump NEW`, and `bb check:versions` passes
* [ ] Changes committed and pushed to `main`
* [ ] Local deploy works: `bb deploy core` (quick smoke check)
* [ ] *First-run matrix passes* — see below

[#first-run-matrix]
=== First-run matrix (pre-release gate)

CI runs `scripts/first-run-smoke.sh` on every push, but only on `ubuntu:24.04`.
Three of the defects found in BOU-232 were invisible to a single image and to
the happy path: a shell the test never used, a network failure the test never
provoked, and a re-run the test never performed.

These two scripts are the broader pass. They are *not* in CI — roughly four
minutes per cell, and they pull whole base images — so they run before a
release, deliberately by hand:

[source,bash]
----
# Environment matrix — each ends in a serving app, or fails loudly
./scripts/first-run-smoke.sh                                    # ubuntu:24.04  (~80s)
SMOKE_IMAGE=fedora:41 ./scripts/first-run-smoke.sh              # ~76s
SMOKE_IMAGE=menci/archlinuxarm:base ./scripts/first-run-smoke.sh   # ~50s, ARM hosts
SMOKE_IMAGE=archlinux:latest SMOKE_PLATFORM=linux/amd64 \
  ./scripts/first-run-smoke.sh                                  # x86 hosts

# Adversarial cases — existing dir, bad names, occupied port, re-run, fish PATH
./scripts/first-run-adversarial.sh                                 # ubuntu:24.04
ADV_IMAGE=fedora:41 ./scripts/first-run-adversarial.sh
ADV_IMAGE=menci/archlinuxarm:base ./scripts/first-run-adversarial.sh   # ARM hosts
ADV_IMAGE=archlinux:latest ADV_PLATFORM=linux/amd64 \
  ./scripts/first-run-adversarial.sh                               # x86 hosts
----

Both exit non-zero on failure, so they can be chained in a release script.

Two results need reading rather than glancing at:

* *SKIPPED is not passed.* The read-only-directory case cannot run as root,
  where permission bits are ignored. It reports SKIP and is counted separately;
  the summary line says so. Treat a skip as a gap, not a green.
* *Arch omits one step.* `install.sh` installs the JVM there with a plain
  `pacman -S`, and pacman cannot sandbox inside a container — under qemu,
  `restricting syscalls via seccomp: 22`; on ARM-native Arch, `Landlock is not
  supported by the kernel`. Neither happens on real Arch hardware. The harness
  pre-satisfies the JVM and prints that the step is excluded.

The port cases delete `/.dockerenv` before running. That is load-bearing:
`port_manager/suggest-port-strategy` checks `docker?` before `dev?`, so a
containerised test otherwise takes the Docker exact-or-fail branch and never
exercises the dev auto-find path a user is actually on.

== Troubleshooting

=== 401 Unauthorized

[source]
----
authentication failed for https://clojars.org/repo/..., status: 401 Unauthorized
----

Work through these causes in order:

==== 1. Account password used instead of deploy token _(most common)_

`CLOJARS_PASSWORD` must be a deploy token, not your login password.
See <<_prerequisites>> for how to generate one.

==== 2. GitHub secret missing or empty

The CI log masks any set value as `***` — even an empty string.
Verify both secrets exist and are non-empty on the `release` environment:
*GitHub → Settings → Environments → `release`*

==== 3. Group `com.wagoe` not verified

Clojars requires proof of domain ownership for groups outside `io.github.*` / `com.github.*`.
The group is the reverse of a domain you control, so `com.wagoe` is proved with
a TXT record on `wagoe.com` itself — not on a subdomain, and not on the docs
site's `wagoe.org`. Add `clojars <your-clojars-username>` there as described at
https://github.com/clojars/clojars-web/wiki/Verified-Group-Names[Clojars: Verified Group Names].

=== Version already exists

[source]
----
Error: version 1.0.0-alpha already exists on clojars
----

Bump the version (`bb bump NEW`) and redeploy.
Deleting an existing version on Clojars is only possible within 24 hours of upload.

=== Dependency not found after deploy

[source]
----
Could not find artifact com.wagoe/wagoe-core:jar:1.0.1-alpha-14
----

. Check that the library was actually published: open `https://clojars.org/com.wagoe/wagoe-core`
. Wait 1–2 minutes for Clojars to finish indexing
. Clear your local Maven cache: +
  `rm -rf ~/.m2/repository/com/wagoe/`

=== CSS not included in ui-style jar

The compiled Tailwind CSS (`daisy-admin.css`, `wagoe-admin.css`) is committed, and CI fails when it is not what the sources build. Rebuild it before packaging all the same.

Locally:
[source,bash]
----
npm ci && npm run build:css
cd libs/ui-style && clojure -T:build deploy
----

In CI this is handled automatically by the workflow's *Build shared UI CSS bundle* step.

=== Inspecting a generated POM

[source,bash]
----
cd libs/core
clojure -T:build clean && clojure -T:build jar
cat target/classes/META-INF/maven/com.wagoe/wagoe-core/pom.xml
----

== Retired coordinates: org.boundary-app

Before the rename the suite published as `org.boundary-app/boundary-<lib>`.
That group is *dormant*: it still exists, nothing is maintained there, and no
further real releases are made from it. It is deliberately not deleted —
deleting it would break every build still pinning an old coordinate and remove
the signpost pointing at the new one.

`bb relocate` publishes one Maven relocation stub per retired artifact:

[source,bash]
----
bb relocate --generate   # write the 29 stub poms to target/relocation/
bb relocate --deploy     # generate, skip already-published, push to Clojars
bb relocate --verify     # check every stub is live
----

Each stub is a `packaging: pom` artifact with no jar, published under
`org.boundary-app` at `1.0.1`, relocating to the library's `com.wagoe`
coordinate at the current suite version.

Both ids are derived, not listed: `relocate/old-artifact-name` takes
`deploy/artifact-name` — which reads the `(def lib …)` coordinate from
`build.clj` — and swaps the `wagoe-` prefix for `boundary-`. So `wagoe-cli`
relocates from `org.boundary-app/boundary-cli`, with no double prefix on either
side.

=== Why version 1.0.1

A stub only surfaces if it becomes the group's newest version. The highest
version already in `org.boundary-app` is `1.0.1-alpha-42` — *not* the
`1.0.0-beta-1` that the Clojars API reports as `latest_release`, since that
field tracks push order while Maven orders `1.0.1` above `1.0.0`. A
qualifier-less `1.0.1` sorts above all of its own alphas, so it is the lowest
version that still wins.

=== What a relocation does not do

[WARNING]
====
Two limits, both measured. Do not expect this to redirect existing consumers.

*Released poms can never gain a relocation.* Clojars refuses to redeploy a
release, so `1.0.0-beta-1` and `1.0.1-alpha-42` keep resolving the old jars
forever. That is not fixable, only outlived.

*tools.deps ignores `<relocation>` entirely.* Verified against MySQL's official
relocation-only pom (`mysql/mysql-connector-java 8.0.33`, no jar published):

[source,text]
----
Error building classpath. Could not find artifact
mysql:mysql-connector-java:jar:8.0.33 in central
----

The Clojure CLI demands a jar at the original coordinate rather than following
the redirect, so for `deps.edn` consumers a relocation buys nothing functional.
Maven consumers do get the real redirect.
====

What the stub does buy is the *Clojars page*: it becomes the newest version, so
every retired artifact displays the deprecation notice and the new coordinate.
Since Clojars renders the latest version's description, publishing a stub is
the only way to change what those pages say.

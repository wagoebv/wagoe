== User Module Observability Reference

How the user module logs, counts and reports errors. There is no manual
instrumentation in the module: two interceptor pipelines from `libs/platform`
do it, one around each HTTP or CLI handler and one around each service
operation.

=== Handler pipeline

`wagoe.user.shell.http` and `wagoe.user.shell.cli` run each request through
`wagoe.platform.shell.interceptors` (`create-http-pipeline`,
`create-cli-pipeline`). The context's `:system` comes from
`wagoe.user.shell.service/interceptor-system`, which carries the
`:logger`, `:metrics-emitter` and `:error-reporter` that `:wagoe/user-service`
is wired with.

Per operation (`op`), `op-metrics` records:

* `<op>.latency.seconds` – duration
* `<op>.success` / `<op>.error` – how the operation ended
* `<op>.failure` – an exception was thrown

`error-capture` reports a thrown exception to the error reporter once, with
`:operation` and `:correlation-id`, after redacting it.

=== Service pipeline

Every `IUserService` method in `wagoe.user.shell.service` runs its body through
`wagoe.platform.shell.service-interceptors/execute-service-operation`, keyed by
operation (`:register-user`, `:authenticate-user`, `:validate-session`,
`:logout-user`, `:logout-user-everywhere`, `:get-user-by-id`, `:list-users`,
`:update-user-profile`, `:deactivate-user`, `:permanently-delete-user`,
`:change-password`, ...). The base pipeline:

[cols="1,3"]
|===
|Interceptor |Does

|`service-operation-start`
|Breadcrumb `Starting <op>`, starts the timer

|`service-operation-logging`
|Logs start, completion and failure. A typed 4xx is logged below error level

|`service-operation-metrics`
|`<op>-attempted`, `<op>-successful`, `<op>-failed` (tag `:reason`), and the
`service-operation-duration` histogram (tag `:operation-type`). No user or
tenant id in the labels

|`service-error-handling`
|Reports 5xx failures once, with tags `:component "service"` and `:operation`. A
typed 4xx is the caller's error and is not reported

|`service-audit-logging`
|Business event `<op>-completed`, and an audit entry when the params carry a
`:user-id`

|`service-success-breadcrumb`
|Breadcrumb `Service operation successful: <op>`
|===

Everything logged or attached to a breadcrumb goes through
`wagoe.core.utils.pii-redaction/redact-for-log` first.

Each interceptor acts only when the `:system` map it is given holds a
`:logger`, `:metrics-emitter` or `:error-reporter`. `:wagoe/user-service` is
wired with `:wagoe/logging`, `:wagoe/metrics` and `:wagoe/error-reporting`, and
passes those three on to every operation. `:validate-session` and
`:get-user-by-id` run on every authenticated request (session and JWT) and get
no logger.

=== Persistence pipeline

`wagoe.user.shell.auth-persistence` wraps its repository calls in
`wagoe.platform.shell.persistence-interceptors/execute-persistence-operation`
(`:find-auth-user-by-email`, `:create-auth-user`, `:set-lockout`,
`:enable-mfa`, ...). It logs them at debug level with their duration, and
failures at their status's level; error reporting is left to the service
layer.

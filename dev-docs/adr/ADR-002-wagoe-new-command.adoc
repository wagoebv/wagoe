== ADR-002: Implement `wagoe new` Command in Scaffolder
:status: Superseded

*Status:* Superseded. `bb scaffold new` was removed in BOU-259; `wagoe new` is the only project generator. +
*Date:* 2026-01-26 +
*Context:* Project Bootstrapping

[IMPORTANT]
====
*Superseded.* This ADR chose to build project bootstrapping into
`wagoe.scaffolder.cli` (Option 2 below). Project generation later moved to the
standalone `libs/wagoe-cli` and its `resources/wagoe/cli/templates/*.tmpl`, but
the scaffolder implementation was left in place. The two then drifted: by
2026-08 a project generated through the scaffolder had no `com.wagoe`
dependencies, no `main.clj`/`system.clj`, no `build.clj`, no `tests.edn` and no
`.env` — 7 files against the CLI's 20 — so it could not boot, test or build.

BOU-259 removed the scaffolder route. `wagoe new` (libs/wagoe-cli) is the only
project generator; the scaffolder generates only what goes *inside* an existing
project. The decision below is kept for the record.
====

'''''

=== Context and Problem Statement

The Wagoe framework currently provides a powerful scaffolder for
adding modules to existing projects, but lacks a built-in mechanism for
bootstrapping new projects. Users are currently expected to manually
clone a starter repository or copy files.

To improve the "Time to First Hello World" and ensure consistent project
structure, we need a `wagoe new` command that can generate a fresh
project based on the standardized Wagoe architecture (Functional Core
/ Imperative Shell).

Additionally, an audit of the current CLI reveals "documentation drift":
the `libs/scaffolder/README.md` documents `--output-dir` and `--force`
flags for the `generate` command, but these are not implemented in
`libs/scaffolder/src/wagoe/scaffolder/cli.clj`.

'''''

=== Decision Drivers

* *Ease of Adoption*: Minimize friction for new users starting their
first Wagoe project.
* *Consistency*: Ensure all new projects follow the latest architectural
patterns (FC/IS, Integrant wiring).
* *Extensibility*: The CLI should be easy to extend without significant
refactoring.
* *Maintenance*: Address existing documentation drift to ensure the tool
behaves as advertised.

'''''

=== Considered Options

==== Option 1: Standalone Bootstrap Script

A separate shell script or Clojure script to clone the starter repo.

* *Pros*: Zero impact on existing scaffolder code.
* *Cons*: Fragmented user experience; harder to maintain as part of the
framework.

[[option-2-extend-scaffolder-cli-white_check_mark-selected]]
==== Option 2: Extend Scaffolder CLI ✅ SELECTED

Add a `new` command to the existing `wagoe.scaffolder.cli`.

* *Pros*: Leverages existing CLI infrastructure, validation patterns,
and service ports. Provides a unified tool for all scaffolding needs.
* *Cons*: Increases the size of `cli.clj`.

'''''

=== Decision Outcome

*Chosen Option:* Option 2: Extend Scaffolder CLI

We will extend the `wagoe.scaffolder.cli` namespace to support a
`new` command. This extension is feasible and clean due to the existing
command dispatch pattern.

==== Implementation Details

[[1-extension-point]]
===== 1. Extension Point

The command will be added to `dispatch-command` in
`libs/scaffolder/src/wagoe/scaffolder/cli.clj` (around line 424):

[source,clojure]
----
(defn dispatch-command [verb opts service]
  (case verb
    :generate (execute-generate service opts)
    :new      (execute-new service opts) ; New case
    :field    (execute-field service opts)
    ;; ...
    ))
----

[[2-new-functions-and-definitions]]
===== 2. New Functions and Definitions

To maintain consistency with existing commands, we will add:

* `new-options`: Definition of CLI flags (`--name`, `--output-dir`,
`--force`, `--dry-run`).
* `validate-new-options`: Validation logic for project names and paths.
* `execute-new`: Orchestration function that calls the service port.

[[3-estimated-effort]]
===== 3. Estimated Effort

* *Estimated LOC*: 150-200 lines of Clojure code in `cli.clj`.
* *New Port*: `ports/generate-project` (to be implemented in the service
layer).

[[4-addressing-documentation-drift]]
===== 4. Addressing Documentation Drift

During the implementation of Phase 2, the following missing flags must
be added to `generate-options` and `new-options` to match the
documentation:

* `--output-dir`: Specify where files are written (defaulting to current
directory).
* `--force`: Overwrite existing files if they exist.

'''''

=== Consequences

==== Positive Consequences

* *Unified CLI*: Users have a single entry point for all scaffolding
tasks.
* *Batteries Included*: Project bootstrapping becomes a first-class
feature.
* *Correct Documentation*: The tool will finally match its README.

==== Negative Consequences

* *Code Growth*: `cli.clj` is already ~760 lines and will grow to ~950
lines.
* *Service Layer Complexity*: The scaffolder service will need new logic
for project-level templates.

'''''

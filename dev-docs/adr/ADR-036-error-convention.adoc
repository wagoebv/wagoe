= ADR-036: One Error Convention — Extending ADR-022 to Return Values
:status: Accepted
:date: 2026-08-18
:deciders: wagoe-team

== Status

Accepted (BOU-322). Extends and partly corrects
xref:ADR-022-error-handling-conventions.adoc[ADR-022], which decided the
*thrown* half of this in April and is still in force. The migration and the
gate are BOU-323.

ADR-022 settled what an exception looks like at the HTTP boundary. It said
nothing about what a function *returns* when it does not throw, and that is
where the drift went: four shapes, none of them decided.

== Context

=== What is actually in the tree

Counted over `libs/*/src` and `src` on 2026-08-18. Two numbers per shape,
because they answer different questions — how many sites *produce* it, and how
many lines *mention* it. A first draft of this ADR quoted the second and called
it the first.

|===
| Shape | Produced | Mentioned | Where

| `(throw (ex-info … {:type …}))`
| 295
| 353
| Everywhere. Decided by ADR-022.

| `{:valid? …}`
| 144
| 180
| Pure decisions. 18 files under `core/`, 14 under `shell/`, 4 elsewhere.

| `{:success? …}`
| 91

=== What ADR-022 already decided, and what drifted from it

ADR-022 is Accepted and mandates `ex-info` with a `:type` keyword, with a
canonical table: `:validation-error` 400, `:not-found` 404, `:unauthorized`
401, `:forbidden` 403, `:conflict` 409, `:redirect` 302, anything else 500.
`wagoe.platform.shell.http.interceptors/http-error-handler` implements exactly
that.

Three things drifted:

* **Dozens of thrown exceptions carry no `:type`.** Around 79 `ex-info` throws
  in `shell/` namespaces have none — heaviest in platform, observability and
  storage. ADR-022 mandated it; nothing enforced it.
* **ADR-022's description of the diagnostic is stale.** It says the check runs
  "when the system configuration includes `{:enforce-error-type? true}`". The
  code reads the profile and `WAG_ENV`, with an override
  (`WAGOE_ENFORCE_TYPED_ERRORS`), and refuses only an `ex-info` whose data map
  lacks `:type` — a bare `RuntimeException` has no `ex-data` at all and passes
  straight to a 500.
* **A second `:type` → status table exists.**
  `wagoe.platform.core.http.problem-details/default-error-mappings` carries 14
  entries (`:user-not-found`, `:auth-failed`, `:business-rule-violation`,
  `:deletion-not-allowed`, …) and is used by admin, storage and the RPC server.
  ADR-022's table is not the only vocabulary.

=== The problem this ADR addresses

A caller composing two Wagoe libraries meets two answers to "it did not work":
one throws, one returns a map — and the map has four spellings. The cost lands
on the person least able to pay it: someone writing their first module against
two of our libraries.

== Decision

=== 1. Thrown errors: ADR-022 stands, and gets enforced

No change to the rule. What changes is that `bb check:error-shape` fails an
`ex-info` thrown in a `shell/` namespace with no `:type` — what ADR-022 asked
for and never got.

Two corrections to ADR-022 while we are here:

* Its enforcement description is replaced by what the code does (above).
* Its "new types should be added here before use" is relaxed: a library may
  define a `:type` of its own, and one that reaches HTTP unmapped is a 500 —
  deliberately, so an unmapped type is visible rather than silently coerced.
  The canonical table remains the vocabulary to reach for first, and
  `problem-details/default-error-mappings` is part of that vocabulary.

Rejected alternative — *return errors as data everywhere*, no exceptions at
shell boundaries. Purer against FC/IS. It also means rewriting 295 throw sites
and both status-mapping tables, and moving failure handling out of the call
stack into every caller's return path. The framework's error DX — the
`:type`-keyed status mapping, the BND classifier that produces BND-201/401/402
from `:type`, the dev enrichment of BOU-321 — is built on the exception
carrying its own type. That investment is the deciding argument.

=== 2. Pure decisions return `{:valid? …}`

A `core/` function that judges something returns data; throwing from the
functional core is what `check:fcis` already forbids.

[source,clojure]
----
{:valid?   false
 :errors   {:email ["missing required key"]}   ;; a map: field -> messages
 :warnings []}                                  ;; optional; omit rather than nil
----

`:errors` is a **map**, the shape Malli's `humanize` produces. Today it is a
vector at roughly 40 sites and a map at 13; the vector form is what migrates.
`:warnings` appears on 31 of 180 `:valid?` lines and stays optional — an absent
key says what an empty vector says, and this ADR will not manufacture work to
make them identical.

One case §2 has to answer explicitly:
`libs/tenant/src/wagoe/tenant/core/tenant.clj` returns
`{:valid? false :error "Tenant not found"}` from a pure function — a
bare-string `:error`, and semantically a `:not-found` that §1 would throw if
core were allowed to throw. It becomes
`{:valid? false :errors {:tenant ["not found"]}}`, and the `shell/` caller
decides whether that is a 404.

=== 3. Expected failure is an answer, and it has one shape

Some failures are not exceptional: a bounced email, an MFA code that does not
match, a push token the provider rejects. The caller asked a question whose
answer can be "no", and throwing would force every caller into `try`/`catch`
for the normal path. These return:

[source,clojure]
----
{:success? false
 :error    {:type    :delivery-failed   ;; keyword, always
            :message "connection refused"}}
----

The line between §1 and §3 is **who was wrong**. If the caller asked for
something impossible or forbidden — a missing entity, an unauthorised action, a
malformed request — that is §1, and it throws. If the request was reasonable
and the world said no, that is §3, and it returns.

Applying that line to the sites that exist is not a formality:

* email, external, push, jobs — the outbound adapters — are §3 and keep their
  shape.
* `libs/workflow`'s service returns
  `{:success? false :error {:type :insufficient-permissions}}`. By the line
  above that is a caller error and belongs in §1. It migrates, and its two
  tests change with it.
* `libs/tenant`'s provisioning returns
  `{:success? true :message "already provisioned"}` and *throws* on every
  failure — it is already §1 with a success value. Its docstring advertises an
  `:errors` vector no code path produces; that docstring is the thing to fix.

`{:success …}` without the question mark (34 sites) is not a variant to bless.
It becomes `:success?` or §1, by the same line.

=== 4. `cognitect.anomalies` is rejected

Zero usages today. It adds a dependency and a third vocabulary to map onto the
two the HTTP layer already reads. The neutrality it buys is worth less than the
mapping layer it costs.

== Consequences

=== The gate (implemented by BOU-323)

`bb check:error-shape` fails when:

* an `ex-info` thrown in a `shell/` namespace has no `:type` in its data map —
  ADR-022's rule, finally enforced. **Around 79 sites fail this on day one**;
  they are the bulk of the migration, and the allowlist is how they burn down;
* a `{:success? false}` map literal has no `:error`, or its `:error` is not a
  map, or the `:type` inside it is not a keyword. Measured: 42 such literals,
  of which about 20 fail today (one missing `:error`, ~6 bare-string `:error`,
  ~14 string `:type`);
* an allowlist entry no longer exempts anything — the burn-down rule the other
  gates use, so the list cannot rot into a drawer.

Three things the gate deliberately does **not** do:

* It does not re-check "core must not throw". `bb check:fcis` already does,
  with `^:wagoe/allow-throw` and `.wagoe/check-fcis.edn` for the namespaces
  that are exempt. Restating it here would duplicate a rule and drop its
  exemptions.
* It does not judge §1 versus §3. That is the reading of a situation, not a
  shape.
* It cannot see computed values — `(assoc result :success? false)`,
  `{:success? (boolean …)}`, `:type (or (:reason check) :forbidden)`. Those get
  reviewed, not gated, and this ADR would be dishonest to imply otherwise.

String literals must be stripped before matching, or two docstrings in
`libs/external`'s tests are false positives on day one.

The allowlist carries a mandatory `:why` per entry, in the flavours
`.wagoe/check-isolation.edn` uses: `BY DESIGN` for the §3 returns that stay,
`TO FIX` for everything else, naming the ticket that removes it.

=== Migration order (BOU-323)

Ordered by blast radius — which is not the order a first draft of this ADR
proposed:

. **The ~79 untyped `shell/` throws.** Mechanical: no consumer reads a key that
  is not there, and it is the rule ADR-022 already made. One structural
  exception — `platform/…/utils/error_handling.clj` rewraps an exception and
  strips `:type` on purpose; that needs a decision, not a keyword.
. **Bare-string `:error` values** in `{:success? false}` returns — devtools'
  dashboard and a handful like it.
. **The ~14 string `:type` values** (external 10, jobs 2, email 1, reports 1).
  *Not* mechanical: `libs/email`'s SMTP adapter reads
  `(get-in result [:error :type] "SmtpError")` out of `libs/external`'s output,
  so the change crosses a library boundary, and five test assertions match the
  strings. Both libraries move in one step.
. **`libs/workflow`** — the `{:success? false}` returns that are caller errors
  become §1.
. **`{:success …}` without the question mark** — scaffolder, storage,
  driver-loader.
. **The 21 `{:error {:type …}}` returns — last, not first.** `platform`'s RPC
  client documents why: an `{:error {:type …}}` *result* must stay
  distinguishable from a transport failure, or the circuit breaker re-sends a
  non-idempotent call. There are 40+ assertions behind it, and the honest
  outcome may be "leave it — it is the right shape for RPC".

=== Costs accepted

* Two shapes for failure (`ex-info`, `{:success? …}`) means a reader decides
  which side of the "who was wrong" line a case falls on. That is a judgement,
  and a smaller one than choosing between five shapes.
* An exception carries no signature. Nothing tells a caller which `:type`
  values a function throws; the `ports.clj` docstring must — and 7 of 27 ports
  files do today. BOU-323 does not fix that; it deserves its own ticket.
* `:type` means something else in RFC 7807: `problem-details` uses it for the
  URI string of a problem type. A gate asserting "`:type` is a keyword" must
  not run against those maps.

=== Known-wrong documentation this ADR does not fix

`docs/modules/architecture/pages/conventions.adoc` states
`:validation-error → HTTP 422`. The interceptor returns 400. Recorded here so
it is not discovered twice; the docs round is BOU-298.

= Authentication & JWT
:description: Setting up authentication, JWT tokens, sessions, and MFA in Wagoe.

Wagoe's `user` library handles the full authentication lifecycle:
user registration, login, JWT tokens, sessions, and multi-factor authentication.

== Prerequisites

[source,bash]
----
export JWT_SECRET="minimum-32-character-secret-key"
----

The JWT secret must be at least 32 characters. Tests that exercise auth also require this variable:

[source,bash]
----
JWT_SECRET="dev-secret-at-least-32-characters-long" clojure -M:test :user
----

== Login

[source,bash]
----
curl -X POST http://localhost:3000/api/auth/login \
  -H "Content-Type: application/json" \
  -d '{"email": "user@example.com", "password": "secret"}'
----

Response:

[source,json]
----
{
  "authenticated": true,
  "sessionToken": "...",
  "jwtToken": "eyJhbG...",
  "user": {"id": "...", "email": "user@example.com", "role": "user"}
}
----

`POST /api/v1/sessions` answers the same. A refused login is an error in the
standard shape (`{"error": {"type", "message", "correlation-id"}}`):

[cols="1,2"]
|===
| Status | When

| 200 with `"requiresMfa": true`
| The password was right; send it again with `mfaCode`.

| 400 `validation-error`
| The body is malformed or the email is not a valid address.

| 401 `unauthorized`
| Wrong email or password. The body is the same whether or not the account exists.

| 401 `mfa-verification-failed`
| Wrong `mfaCode`.

| 403 `mfa-enrolment-required`
| MFA is required and the user has not enrolled.

| 429 `account-locked`
| Too many failed attempts. `Retry-After` gives the seconds to wait. Unlike the 401, this tells the caller the account exists.
|===

== Protected routes

Add the auth interceptor to routes that require authentication:

[source,clojure]
----
[["/profile"
  {:get {:handler      handlers/get-profile
         :interceptors ['auth/require-authenticated]
         :summary      "Get current user profile"}}]]
----

== Multi-Factor Authentication (MFA)

MFA uses TOTP (Time-based One-Time Passwords, compatible with Google Authenticator / Authy).

=== Setup flow

[source,bash]
----
# 1. Start MFA setup (returns a secret + QR code URL)
curl -X POST http://localhost:3000/api/auth/mfa/setup \
  -H "Authorization: Bearer <token>"

# 2. Enable MFA (verify with first TOTP code)
curl -X POST http://localhost:3000/api/auth/mfa/enable \
  -H "Authorization: Bearer <token>" \
  -H "Content-Type: application/json" \
  -d '{"secret": "...", "verificationCode": "123456"}'
----

=== Login with MFA enabled

[source,bash]
----
curl -X POST http://localhost:3000/api/auth/login \
  -H "Content-Type: application/json" \
  -d '{"email": "user@example.com", "password": "secret", "mfaCode": "123456"}'
----

[#mfa-per-login]
=== Deciding per login

By default a login asks for a code exactly when the user turned MFA on. To decide
per login, name a function under `:auth`:

[source,clojure]
----
:wagoe/user {:auth {:mfa-required? my.app.auth/mfa-required?}}
----

[source,clojure]
----
;; Skip MFA on the office network, require it everywhere else.
(defn mfa-required? [_user {:keys [ip-address]}]
  (not (office-network? ip-address)))
----

It gets the user and the login context (`:ip-address`, `:user-agent`, and
`:provider` for an OpenID Connect sign-in) and applies to password and OpenID
Connect logins alike. Returning false waives the code; MFA stays on for the user.
Returning true for a user without MFA refuses the login: enrolling needs a
signed-in user, so they must sign in where MFA is not required, or ask an
administrator. The symbol is resolved at boot, and one that does not resolve stops
the boot. A function that throws fails the login.

A hook that needs one of your components, say the allowed networks kept in the
database, comes from an application module instead. Its `ig-config` contributes it:

[source,clojure]
----
(defn ig-config [_settings _ctx]
  {:components {:wagoe/office-networks {:db (ig/ref :wagoe/db-context)}}
   :auth       {:mfa-required? (ig/ref :wagoe/office-networks)}})
----

The component is a function of the same two arguments, or implements
`wagoe.user.ports/IMfaPolicy`. Each system runs its own, so a test system and a dev
system in one JVM do not share state. Setting the hook both in config and from a
module, or from two modules, stops the boot.

WARNING: Behind a reverse proxy, set `:wagoe/http :trusted-proxies` before keying a
hook on `:ip-address`; without it every login carries the proxy's address.

=== Disable MFA

[source,bash]
----
curl -X POST http://localhost:3000/api/auth/mfa/disable \
  -H "Authorization: Bearer <token>" \
  -H "Content-Type: application/json" \
  -d '{"verificationCode": "123456"}'
----

[#oidc]
== Sign in with OpenID Connect

Any OpenID Connect provider (Google, Microsoft Entra, Keycloak, Auth0, …) can sign
people in to the web UI. Name each provider under `:wagoe/user`:

[source,clojure]
----
:wagoe/user
{:oidc {:base-url  "https://app.example.com"   ; where the provider redirects back
        :providers {:google {:issuer        "https://accounts.google.com"
                             :client-id     #env GOOGLE_CLIENT_ID
                             :client-secret #env GOOGLE_CLIENT_SECRET
                             :scopes        ["openid" "email" "profile"]  ; the default
                             :label         "Google"                      ; button text
                             :link-by-email? false                        ; the default
                             :trust-email?   false                        ; the default
                             :auto-create?   false}}}}                    ; the default
----

Register `<base-url>/web/auth/oidc/<provider>/callback` as the redirect URI at the
provider. The login page then shows a "Sign in with Google" button.

The flow is the authorization code flow with PKCE. The discovery document and the
provider's signing keys are fetched and cached for an hour. The id token's signature,
issuer, audience, expiry (60 seconds of clock skew allowed) and nonce are checked. The
state, nonce and PKCE verifier travel in an encrypted cookie that expires after ten
minutes, so any replica can finish a sign-in another one started.

Which account a sign-in belongs to:

. The account already linked to the token's issuer and subject. That link outlives an
  email change at the provider.
. Otherwise, with `:link-by-email?`, the account with the token's email, and only when
  the provider marks that email verified. The link is stored from then on. An
  administrator account is never linked this way; the sign-in is refused.
. Otherwise, with `:auto-create?`, a new account with role `:default-role` (`:user`, or
  `:viewer`; never `:admin`) and no usable password.
. Otherwise the sign-in is refused.

Some providers, Microsoft Entra among them, send no `email_verified` claim, so no email
counts as verified. `:trust-email? true` on such a provider treats its `email` claim as
verified.

WARNING: Set `:trust-email?` only for a single-tenant issuer you control. Anyone who can
put an arbitrary address in that provider's `email` claim can then sign in as the account
with that address. Multi-tenant issuer templates such as
`https://login.microsoftonline.com/{tenantid}/v2.0` are refused; name one tenant.

A successful sign-in opens the same database session a password login opens. The same
account rules apply: a deactivated or locked account cannot sign in, and MFA is asked
for after the provider by the same rule as a password login (<<mfa-per-login>>). Wrong
codes count towards the lockout.

The cookie key derives from `JWT_SECRET`; set `:state-secret` under `:oidc` to use
another. The client secret is sent with HTTP Basic; set `:token-endpoint-auth :post` on
a provider that wants it in the form body. Leave `:client-secret` out for a public
client.

== Landing page and dashboard

After signing in, an administrator lands on `/web/admin/users` and everyone else on
`/web/dashboard`, a generic page the user module serves. Both are configurable under
`:wagoe/user`:

[source,clojure]
----
:wagoe/user
{:login-redirect {:user "/web/overzicht" :default "/web/overzicht"}  ; by role
 :dashboard      false                                                ; or {:handler my.app.web/dashboard}
 :home           "/web/overzicht"}                                    ; where the layouts link home
----

`:login-redirect` is a map of role to path (`:default` covers roles it does not name,
and unnamed keys keep the defaults above), or a symbol naming a function of the user
and the login context (`:ip-address`, `:user-agent`, `:request`) that returns a path.
An application module can contribute it as `:auth {:login-redirect (ig/ref …)}`, a
function or a `wagoe.user.ports/ILoginRedirect`, the same way as `:mfa-required?`. A
function that returns nil or a path off this site sends the user to the default. It applies to password login, the MFA step, OpenID Connect sign-in and
`/web` for someone already signed in. A `return-to` on this site still wins.

`:dashboard false` leaves `/web/dashboard` to the application; `{:handler sym}` serves
that Ring handler there instead, behind the same sign-in check.

`:home` is where the logo, "back" and dashboard links in the built-in layouts point. It
defaults to `/web/dashboard`, or to `/web` with `:dashboard false`, which sends a
signed-in user on to their landing page. All three keys are checked at boot: a path off
this site, an unknown role or a symbol that does not resolve stops it.

== Groups and permissions

A group has a name, members and grants. A grant is a permission, a keyword your
application defines, and a scope, a map of whatever narrows it. A member holds the
grants of every group they are in. Wagoe stores and checks them; what a scope means is
up to the application. The `:admin` role needs no group.

Administrators manage groups at `/web/admin/groups`. Joining or leaving a group and a
changed grant are written to the audit trail of each user whose rights change.

Declare what a grant may name, so a bad one is refused. Each is a Malli schema or a
symbol naming one:

[source,clojure]
----
:wagoe/user
{:groups {:permissions [:enum :invoice/approve :invoice/view]
          :scope       [:map {:closed true}
                        [:domain-id {:optional true} :int]
                        [:director-general-id {:optional true} :uuid]]}}
----

Without them any keyword and any map of EDN values is accepted. A scope is stored as
EDN, so a uuid or keyword in it reads back as one.

Check grants on each request; nothing is cached, so a change applies to the next one:

[source,clojure]
----
(require '[wagoe.user.ports :as user-ports]
         '[wagoe.user.core.group :as group])

;; group-service is :wagoe/user-group-service
(let [grants (user-ports/user-grants group-service (:user request))]
  (group/holds? grants :invoice/view)                          ; in any scope
  (group/grants-for grants :invoice/approve)                   ; => [{:domain-id 4} …]
  (group/authorized? grants :invoice/approve #(= domain-id (:domain-id %))))
----

A soft-deleted user holds no grants. Deleting a user or a group removes the
memberships, and a group's grants go with it.

[#web-ui-off]
== Turning the web UI off

An API-only deployment can drop the user module's HTML pages:

[source,clojure]
----
:wagoe/settings {:features {:user-web-ui {:enabled? false}}}
----

The shipped configs read it from `WAG_WEB_UI_ENABLED`, so `WAG_WEB_UI_ENABLED=false`
does the same. It defaults to on.

[cols="1,1",options="header"]
|===
| Removed | Kept

| `/web` landing page, `/web/login`, `/web/register`, `/web/logout`
| `/api/v1/auth/login`, `/api/v1/sessions`, `/api/v1/sessions/:token`

| `/web/dashboard`, `/web/profile/**` (incl. MFA setup and disable pages)
| `/api/v1/auth/mfa/**`

| `/web/users/**` (user management, sessions), `/web/audit`
| `/api/v1/users/**`

| `/web/admin/groups/**`
| OpenID Connect sign-in, when providers are configured
|===

Other modules are not affected: `/` still redirects to `/web/login`, and the admin UI
stays mounted while `:wagoe/admin` is active. Groups have no API; manage them through
`:wagoe/user-group-service`.

== Session management

[source,bash]
----
# List active sessions
curl http://localhost:3000/api/auth/sessions \
  -H "Authorization: Bearer <token>"

# Revoke a specific session
curl -X DELETE http://localhost:3000/api/auth/sessions/{session-id} \
  -H "Authorization: Bearer <token>"
----

[#csrf]
== CSRF protection

State-changing web requests are protected against Cross-Site Request Forgery by the
`http-csrf-protection` interceptor (in the default stack). A POST/PUT/DELETE/PATCH is
validated — and rejected with `403` on a missing or invalid token — when it is either
session-authenticated or targets a `/web` route. This covers the web UI, `/web/admin`,
and any session-authenticated `/api` route. Token-auth API clients that send only a
bearer token (no session cookie) are not CSRF-vulnerable and are not checked.

How a token reaches the browser and back:

* On a page load the interceptor issues a session-bound token and the shared layout
  renders `<meta name="csrf-token" content="…">`.
* For HTMX requests, a global `htmx:configRequest` listener copies that token into the
  `X-CSRF-Token` header automatically — no per-form work.
* Plain `<form method=post>` forms carry it in a hidden `__anti-forgery-token` field
  (added via `(wagoe.platform.core.csrf/hidden-field)`).

Unauthenticated flows (login, register, MFA) have no session yet, so the token is bound
to a `SameSite=Strict` `csrf-session` cookie minted on the page GET and validated on the
subsequent POST.

Configure under `:wagoe/http :security :csrf`:

[source,clojure]
----
:security {:csrf {:enabled?     true
                  :secret       #or [#env CSRF_SECRET #env JWT_SECRET]
                  :exempt-paths ["/api/v1/payments/webhook"]}}  ; webhooks/callbacks
----

The secret defaults to `JWT_SECRET`, so deployments are protected even without an
explicit `:csrf` block. Disable it (`:enabled? false`) only in test/dev. List endpoints
that legitimately cannot send a token (PSP webhooks, OAuth callbacks) under
`:exempt-paths`; a trailing `/*` matches on a path-segment boundary.

See xref:libraries:platform.adoc#csrf-protection[platform library → CSRF protection] for
the interceptor internals and token format.

== Key security notes

* `JWT_SECRET` must be set; missing it causes startup failures (it is also the default
  CSRF signing secret)
* CSRF protection is enforced for session-authenticated, state-changing requests — see
  <<csrf>>
* Internal entities use `:password-hash` (kebab-case) — never `:password_hash`
* The `user` library enforces account lockout after repeated failed login attempts

See xref:libraries:user.adoc[user library] for the full reference.
